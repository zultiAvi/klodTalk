Coder Output — "Summarize My Requests" button + server handler
================================================================

Implemented per /workspace/.klodTalk/team/current/plan.md.

Summary
-------
Added a new direct WebSocket request/response (not a broadcast role): the user
clicks "Summarize My Requests" on the session header; the server filters the
session history to messages with role == "user" (owned by the session owner),
runs Claude (prompt piped via stdin to avoid ARG_MAX), and returns the summary
in a dedicated overlay panel on the web client. Android wires the message-type
constant + send helper + a no-op receive branch for forward compatibility (no
Android UI — matches existing Analyze convention).

Files touched

NEW   server/prompts/summarize_my_requests.md
MOD   server/server.py
        - Added module-level caches:
            _session_user_summaries: dict[tuple[str, str], tuple[str, int]]
            _session_user_summaries_running: set[tuple[str, str]]
        - Added handle_summarize_my_requests(ws, user_name, data)
            * validates session exists, user is a member, user IS session owner
            * loads history (closed -> archive jsonl; open -> history_store)
            * filters role == "user"; returns error if empty
            * cache key = (session_id, user_name); cache hit returns cached=True
            * if a run is in flight, returns status=running
            * otherwise launches asyncio.create_task(_run_user_summary(...))
        - Added _run_user_summary(...)
            * loads prompt from server/prompts/summarize_my_requests.md
            * builds history_text (truncated at 100_000 chars)
            * invokes claude with -p "-" and input=full_prompt (stdin pipe —
              follows skill claude-prompt-stdin-arg-max)
            * parses JSON output -> result
            * stores in cache, sends complete only to the requesting user via
              connected_clients[user_name] (per-user, not broadcast)
            * on exception sends status=error to the requesting user
            * finally removes running flag
        - Registered dispatcher in handle_client:

Deviations from plan
--------------------
None of substance. The plan offered two cache schemas (session_id key vs.
(session_id, user_name) key); I implemented the per-(session, user) keying as
recommended for correctness. The plan also offered two filter strategies
(restrict to session owner, or add per-message author tracking); I implemented
strategy (a) — owner-only — as the plan specified, returning a friendly error
to non-owners ("Only the session owner can summarize their requests.").
