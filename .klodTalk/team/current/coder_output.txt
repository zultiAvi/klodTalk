## What was changed and why

### Idea 1 -- SessionStart sessionTitle hook
Plan steps: create hook script, register in settings.json, document skill.

- Created /workspace/server/utils/hooks/session_start_title.sh: reads
  KLODTALK_PROJECT and KLODTALK_ROLE env vars (with graceful fallbacks to
  "unknown" / "agent" per instinct that env vars may not be set), sanitizes
  them (tr -d control chars, head -c length cap), and emits the v2.1.153+
  hookSpecificOutput envelope with sessionTitle = "klodtalk/<project>
  [<role>]" and reloadSkills: false. Exit-0 discipline applied via
  { ... } 2>/dev/null + exit 0.
- Registered a SessionStart hook group in /workspace/.claude/settings.json
  with "matcher": "" (per instinct: matcher field required). Placed before
  the existing PostToolUse group for readability; ordering does not affect
  dispatch.
- Created /workspace/CLAUDE/skills/session-start-title.md documenting the
  pattern, env-var sources, the reloadSkills capability (currently false;
  reserved for future hot-reload), the v2.1.153+ version requirement, and
  the registration snippet.

Why: KlodTalk runs many concurrent Docker-per-role sessions; today they all
appear identical in Claude Code logs. Per-session titles make operator log
correlation trivial without touching server code.

### Idea 2 -- Fresh-context evaluator role
Plan steps: create role file with disallowedTools, document skill, do NOT
modify any existing team file.

- Created /workspace/teams/roles/reviewer_fresh_context.md. Frontmatter
  forwards mcpServers (filesystem) and disallowedTools (Bash, Write, Edit,
  MultiEdit, NotebookEdit) -- only the two keys run_agent.py parses
  (instinct: role frontmatter only forwards these two). Includes
  <!-- inherits: base.md --> per role-inheritance-pattern.md. Prompt
  establishes:
    * No prior conversation history (fresh context).
    * Default verdict per criterion = FAIL until evidence is read.
    * Artefact-only inputs (in_message.txt, plan.md, changed_files.txt,
      *_output.txt, and the actual changed files).
    * Output written to reviewer_output.txt in the SAME schema as the
      regular reviewer so downstream tooling (reviewer-exit-condition-
      scoring.md consumers) keeps working.
    * Required "## Fresh-Context Reading Log" section listing which
      artefacts were opened -- makes drive-by APPROVAL verdicts visible.
    * Exit Condition Check section matching reviewer-exit-condition-
      scoring.md (n/10, < 7 -> BLOCKER).
- Created /workspace/CLAUDE/skills/fresh-context-evaluator.md documenting
  the design rationale, default-FAIL contract, opt-in pattern for teams,
  and the safety note explaining why nightly_scout.md was NOT modified.

Why: KlodTalk's nightly pipelines run unattended; the regular reviewer
shares context with the coder and can inherit framing bias. A fresh-
context evaluator is a complement (not replacement) that any team can opt
into by adding the role to its members table.

### Idea 3 -- agent_type / agent_id in hook payloads
Plan steps: modify post_tool_use_logger.sh, modify sanitize_bash_output.sh,
document skill. Observability only -- no behavioural branching.

- Modified /workspace/server/utils/hooks/post_tool_use_logger.sh: added
  agent_id and agent_type fields to the jq JSONL builder (with `// null`
  fallbacks for older SDKs). Inline comment cites the SDK source. Exit-0
  discipline unchanged.
- Modified /workspace/server/utils/hooks/sanitize_bash_output.sh: added
  agent_id and agent_type to the telemetry JSONL entry. Inline comment
  explicitly notes this is observability-only -- NO branching of the
  redaction logic per role, per the safety guidance in the plan.
- Created /workspace/CLAUDE/skills/hook-agent-type-filter.md documenting
  the new payload fields, the jq snippet, a future per-role branching
  sketch (clearly marked "NOT yet enabled"), the security note that
  agent_type is not a trust boundary, and links to the actual security
  primitives (disallowedTools, pre-tool-use-guard).

Why: KlodTalk's existing hooks are role-agnostic. Capturing agent_type in
the JSONL telemetry enables operators to correlate hook events to roles
without touching the per-role settings.json layout. Branching on the
field is deferred behind a future security review per the prompt's
instructions.

## Known limitations / follow-up
- session_start_title.sh requires Claude Code v2.1.153+. Older CLIs ignore
  the sessionTitle field silently; not a regression. Dockerfile.agent is
  pinned to @2.90.0 (>= 2.1.119) -- verify it also satisfies 2.1.153
  before relying on the title in operator workflows.
- reloadSkills is hard-coded to false; the deferred-ideas section calls
  out the missing live-session signal path needed before this can flip.
- The fresh-context evaluator is not yet wired into any team. Operators
  who want a second-opinion review must opt in by editing their own team
  .md (see the skill file for the members-table snippet).
- agent_type branching in hooks is deliberately NOT enabled -- JSONL
  telemetry only. Future change should go through a fresh-context review
  before flipping any policy branches.
- KLODTALK_PROJECT / KLODTALK_ROLE env-var injection by run_agent.py was
  not directly inspected in this session; the hook degrades to
  "unknown"/"agent" if either is missing, so worst case is a less
  informative title rather than a failure.
