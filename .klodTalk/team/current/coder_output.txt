## Idea 1: $CLAUDE_EFFORT in PostToolUse Hook Logger

What changed and why:
- `server/utils/hooks/post_tool_use_logger.sh`: capture `EFFORT="${CLAUDE_EFFORT:-}"`
  before the jq pipeline. Added `--arg effort` and an `effort_level` field to the
  jq object, using `if . == "" then null else . end` so empty values are emitted as
  JSON null (matches the existing convention for other optional fields).
- Raw-fallback branch: added `"effort_level":"${EFFORT}"` to the emitted JSON. Also
  guarded the inner `jq -Rs .` invocation with a fallback to `""` so the fallback
  path stays robust if jq is partly unavailable.
- Hook still exits 0 unconditionally; entire body is wrapped in `{ ... } 2>/dev/null`.
- `CLAUDE/skills/hook-event-logging.md`: documented the new `effort_level` field
  under Quick Reference, listed all emitted JSONL fields, and added an "Environment
  Variables in Hooks" subsection covering `$CLAUDE_EFFORT` (Claude Code v2.1.136+)
  and a cross-reference noting `$CLAUDE_CODE_SESSION_ID` is NOT available in hooks.

Verification: smoke-tested the script with `CLAUDE_EFFORT=high` (logged
`effort_level: "high"`) and with the variable unset (logged `effort_level: null`).
Both invocations exited 0. The two test lines appended to hook_events.jsonl during
verification were removed afterwards.

## Idea 3: autoMode.hard_deny for Read-Only Roles -- FALLBACK PATH TAKEN

Verification performed (per operator instructions):
1. `teams/CLAUDE.md` and `teams/roles/base.md`: NO mention of a `settings:`
   frontmatter key.
2. `server/run_agent.py` searched for `settings|frontmatter|mcpServers|disallowedTools|autoMode`:
   the only `settings` matches are the runtime mutation of `.claude/settings.json`
   to install hook configurations -- there is NO code that reads role-file
   frontmatter and forwards a `settings:` block into `.claude/settings.json`.
3. Grep for `autoMode|hard_deny` across the entire repo returned zero hits.
4. The existing `mcp-frontmatter` skill explicitly documents that frontmatter is
   "forward-looking -- not yet parsed natively by orchestrator." The same caveat
   applies to any hypothetical `settings:` block.

Conclusion: adding `settings: { autoMode: { hard_deny: true } }` to role frontmatter
today would be a silent no-op. Per the operator's verification protocol, I took the
fallback path.

What changed and why:
- Created `CLAUDE/skills/auto-mode-hard-deny.md` documenting:
  - The setting key (`autoMode.hard_deny: true`) and its semantics.
  - The verified-correct placement today: operator-level `.claude/settings.json`
    for the relevant agent container (the same file mutated by
    `server/run_agent.py`).
  - The forward-looking role-frontmatter form for when orchestrator parsing lands.
  - Layering guidance with `disallowedTools` (defense-in-depth).
  - Explicit "do NOT apply" list (coder, planner, executor, etc.).
- Added an HTML comment block (between the frontmatter and the heading) to both
  `teams/roles/reviewer.md` and `teams/roles/qa_analyst.md` pointing at the new
  skill and warning future editors NOT to add an unsupported `settings:` key until
  orchestrator support lands. Existing frontmatter (`disallowedTools` and, for
  reviewer, `mcpServers`) was left untouched.
