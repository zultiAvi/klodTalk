## What Was Changed and Why

Implemented the top 3 ideas from evaluated_ideas.md:

1. **GitHub MCP Server for the Scout Role** -- Replaced fragile WebSearch-based
   GitHub discovery with the official authenticated MCP server. Added
   `mcpServers.github` YAML frontmatter to `teams/roles/github_scout.md` (using
   `npx -y @modelcontextprotocol/server-github`) and updated the role body to
   prefer MCP tool calls over raw WebSearch. Documented the pattern in a new
   skill `CLAUDE/skills/github-mcp-scout.md`. Operators must export
   `GITHUB_PERSONAL_ACCESS_TOKEN` on the host for the env var to propagate into
   the agent container.

2. **Three-Tier Model Routing Skill** -- New skill at
   `CLAUDE/skills/three-tier-model-routing.md` encoding the Opus/Sonnet/Haiku
   decision rule: Opus for committed output (Coder/Fixer), Sonnet for
   reasoning-heavy non-write roles (Planner/Reviewer/Evaluator), Haiku for pure
   I/O (Scout/Broadcaster). Includes anti-patterns and cost notes that link to
   `model-version-hygiene.md` for active model IDs.

3. **PreToolUse Destructive-Command Blocker Hook** -- New script
   `server/utils/hooks/pre_tool_use_guard.sh` (executable). Reads stdin JSON,
   inspects `tool_input.command` only when `tool_name == "Bash"`, and refuses a
   narrow deny-list (`rm -rf`, `git reset --hard`, `git push --force|-f`,
   `chmod 777`, `dd ... of=/dev/`, `mkfs`, `shutdown`, `reboot`) by exiting 2
   with an actionable stderr message. Uses `jq` with a `grep`/`sed` raw
   fallback (mirrors `post_tool_use_logger.sh`). Smoke-tested:
   `rm -rf /workspace` blocked, `ls -la` allowed, `git push --force` blocked,
   non-Bash tool calls passed through. Companion skill
   `CLAUDE/skills/pre-tool-use-guard.md` documents the hook, the deny-list,
   the `continueOnBlock: true` + `matcher: "Bash"` registration in
   `.claude/settings.json`, and the instincts.md-line-7 caveat (role frontmatter
   does NOT forward `hooks`, so registration is container-level only).

### Self-Assessed Risk Areas
- Deny-list false positives: the regex patterns are intentionally narrow, but
  worth reviewing whether any legitimate Coder workflow (e.g., a refactor that
  runs `rm -rf node_modules`) would now be blocked. Mitigation: hook uses
  `continueOnBlock: true`, so a block is recoverable feedback, not a session
  kill.
- MCP env-var propagation: the role frontmatter uses
  `${GITHUB_PERSONAL_ACCESS_TOKEN}` expansion; per instincts.md line 7 only
  `mcpServers` and `disallowedTools` are forwarded. Worth a Reviewer check that
  the env section inside `mcpServers.github` is honoured by the current
  orchestrator -- if not, the expansion needs to happen at container env level
  via `server/run_agent.py` (out of scope here).
- Skill-only changes (idea 2): no functional risk; the risk is that an
  unreviewed audit step against the 20 existing teams was deferred (mentioned
  as "secondary step" in evaluated_ideas.md). Listed here as scope, not bug.

### Questions for Reviewer
- Does the current orchestrator (`teams/run_claude_team.sh` / `run_agent.py`)
  honour the `env:` sub-block under an `mcpServers.<name>` entry, or does
  `GITHUB_PERSONAL_ACCESS_TOKEN` need to be exported at the docker-run level
  instead?
- Is the deny-list regex for `rm -rf` (`rm[[:space:]]+-[a-zA-Z]*r[a-zA-Z]*f`)
  acceptably narrow, or should we restrict it further (e.g., require an
  absolute-path argument) to avoid blocking benign `rm -rf build/`?
